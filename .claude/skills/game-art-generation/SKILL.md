# ゲームの絵の作り方（Gemini API）

絵はゲームの第一印象を決める。1枚浮くだけで作品全体の印象が落ちるので、
「とりあえず用意する」ではなく、**基準に合わせて作り、実測で確かめてから出す**。

このスキルは**どのゲームでも使える汎用手順**。作品ごとに違う部分（キャラの基準・配色・頭身）は
**リポジトリ側のスタイル文書から読む**（下記「プロジェクトの基準を先に読む」）。

---

## 0. プロジェクトの基準を先に読む

生成に着手する前に、その作品の「正」を必ず把握する。**あとから直すのは高くつく**。

```bash
# 作業中のリポジトリで、この順に探す
ls ART_STYLE.md CLAUDE.md STYLE.md docs/art*.md 2>/dev/null
ls images/ assets/ 2>/dev/null | head -30
ls tools/gemini-*.mjs 2>/dev/null        # 既存の生成スクリプト＝作法の実例
```

見るべきもの:

| 何を | どこから |
|---|---|
| **キャラの正**（顔・配色・頭身） | スタイル文書。無ければ「一番出来の良い既存絵」を基準画像として扱う |
| **同系統の既存絵** | 新しい絵はこれと並ぶ。並べて浮かないことがゴール |
| **画像の実寸と用途** | 描画コードの `drawImage(...)` の引数。⚠正方形で書き出すと横長のものが潰れる |

スタイル文書が無い作品なら、**最初の1枚を作る前にユーザーと基準を決める**。
「何を基準に揃えますか」と聞くのは、あとで全部作り直すより安い。

> 例（ぴよ氏の冒険）: キャラの正 = `images/title.jpg`、細部の正 = `ART_STYLE.md`、年齢の正 = `images/shop05.jpg`。
> 絶対条件は「萌え美少女アニメ顔」「頭身を下げない（あごから靴底が頭3個分以上）」「黄色い猫耳カチューシャ」。

## 1. そもそも生成するものか？（手続き描画との切り分け）

| 対象 | どうする |
|---|---|
| 背景・地形・ギミック（洞窟の壁、床、扉、溶岩、光柱、魔法陣、UIの枠…） | ✅ canvas で直接描いてよい |
| **キャラクター**（人物・敵・ボス・店員の顔） | ❌ 手続き描画は**禁止**。生成AIで作る |
| **アイテム**（ショップ品・ドロップ品・アイコン類） | ❌ 手続き描画は**禁止**。生成AIで作る |

手続き描画のキャラ／アイテムは、生成AIの絵と並べると確実に浮く。
だから「手続きで描きます」という提案自体をしない。

⚠**既存の絵を流用して済ませた場合は、その場で必ず申告する。** 流用は悪ではないが、黙るのは駄目
（ぴよ氏の冒険で、地底入場パスに別アイコンを黙って流用して指摘された前例がある）。

## 2. 3種類のどれか？ — 作り方が根本的に違う

| 種類 | 例 | 手順書 |
|---|---|---|
| **スプライト／アイコン**（透過が要る小さい絵） | ショップの品、ドロップ品、図鑑アイコン | `references/sprite-icon.md` |
| **一枚絵／カットイン**（不透明・キャラが大きく写る） | 店内、チュートリアル、エンディング | `references/artwork.md` |
| **モーション差分**（歩行・飛行の連番コマ） | 歩行4コマ、羽ばたき | `references/motion-veo.md` |

⚠**モーション差分を1枚ずつ独立生成するのは絶対禁止。** 同じポーズを指定してもコマ間で形と色が揺れ、
動きが必ず崩れる。過去に2回やらかしてクレジットを溶かしている。必ず動画からコマ切り出しにする。

## 3. 環境（ここで詰まりやすい）

```bash
zsh -ic 'cd <リポジトリ>/tools && node gemini-xxx.mjs'
```

- 生成先は **Gemini API**。既定モデル `gemini-3-pro-image`（Nano Banana 2）、SDK は `@google/genai`
- ⚠**鍵 `GEMINI_API_KEY` は通常のシェルには無い。** 必ず `zsh -ic` 経由で実行する。
  素の `env` で見えないからといって「鍵が無い」と判断しないこと（実際に誤認した前例がある）
- OpenAI（`gpt-image-1`）は**クレジット切れで終了**。`generate-*-openai.mjs` 系は
  過去の記録として残っているだけで、叩いても課金が通らない。**プロンプトの作法だけ参考にする**

## 4. 全体の流れ

```
① スタイル文書と同系統の既存絵を読む（§0）
      ↓
② tools/gemini-<name>.mjs を書く（雛形 scripts/template-gemini-sprite.mjs を複製）
      ↓
③ 候補を n=2〜4 生成 → tools/_raw/ に置く（本番ディレクトリにはまだ入れない）
      ↓
④ ⚠自分で見て、実測で検品する（目分量で判断しない）
      ↓
⑤ ⚠**同じターンでユーザーに見せる**（SendUserFile / display:"render"）
      ↓
⑥ ユーザーが選ぶ → `--pick=key:番号` で本番へ配置
```

### ⑤ が最重要 — 生成したら必ずそのターンで見せる

**画像を生成したら、生成したそのターンの中で必ず表示する。例外なし。**

- 文章で「候補3枚できました」と説明するだけで**画像を出さないのは違反**。
  ユーザーは画像を見られないので**判断できない**
- **「見せてほしい」と言わせるのも違反。** 別ターンで出し直すのは無駄な手間をかけさせている
- 手段は `SendUserFile` の `display: "render"`。**候補は全部出す**。比較用に作った検品画像も一緒に出す
- ⚠**検品は表示の前に済ませる。ただし検品を理由に表示を次のターンへ遅らせてはいけない。**
  同じターンで「生成 → 検品 → 表示」まで完了させる

### ④ の検品 — 「自分で見る」と「実測する」の両方

**画像は Read で直接見られる。**（「AIは画像を認識できない」という古い前提は失効している）
細部は `ffmpeg` でクロップ＋拡大すれば読める。だから**見もせずに出さない**。

目で見て分かりにくいもの（絵柄の粒立ちのばらつき等）は数字で測る。
ぴよ氏の冒険には `tools/measure-grain.mjs` があり、「色が同じとみなせる画素の連続長」を粒として測る
（模擬ドット絵は格子が焼き込まれていないので、この測り方でないと測れない）。
⚠キャラ部分を `--region` で指定すること。背景は平らな面が広く、粒が実際より大きく出る。

**ただし数値の合格帯は「採用の理由」にも「却下の理由」にもならない。**
数値は目視の裏を取る道具で、最終判定はユーザーがする。
検品は「見せる候補を整える」ことであって、**OKテイクを勝手に落としてよい免罪符ではない**。

## 5. クレジットの使い方（叱られた実績あり）

- **動画（Veo）は1本ずつ。** 生成したら必ず結果を見せて判断を仰いでから次を撮る。
  確認なしで2本続けて生成し、3本目に着手しかけて叱られた前例がある
- 静止画の候補は n=2〜4 程度。同じプロンプトで無限に引き直さない。
  外れ続けるならプロンプトを直す（`references/` に、実際に効いた直し方が書いてある）
- **生成コマンドを打つ前に「直前の生成物をユーザーに見せたか？」を自問する。** 見せていなければ生成しない

## 詳細な手順書

- `references/sprite-icon.md` — 透過スプライト／アイコン。⚠**Gemini は透過PNGを返さない**のでクロマキーする
- `references/artwork.md` — 一枚絵。参照画像の渡し方、頭身の縛り方、絵柄の揃え方
- `references/motion-veo.md` — モーション差分。動画 → コマ切り出し → 整列
- `scripts/template-gemini-sprite.mjs` — 生成スクリプトの雛形（`tools/` へ複製して使う）
